# SCIO firmware and transform-recovery notes

Living log for offline SCIO decoding. Preserve negative results because they
constrain later work. See `EVIDENCE.md` for the fact/hypothesis ledger and
acceptance thresholds.

## What local evidence establishes

- The apps transmit the dark, sample and gradient bytes verbatim to the server.
- Available `-e` blobs have an observed 8-byte prefix followed by bodies of
  1792/1792/1648 bytes. The bodies are high entropy and 16-byte aligned.
- The prefix type word is 0 for dark/sample and 110 for gradient. The second
  word varies and is not classified.
- No inspected Android app contains a local spectral decoder.
- The device exposes firmware/table headers over USB, but tested read-only
  commands did not return their bodies.

These facts do not identify encryption, a cipher, an IV/nonce, a key derivation,
or Lockbox activation. Packing, compression and obfuscation remain alternatives.

## Local artifact recovery

The apps handled files named `ble`, `dsp_boot`, `dsp_dec`, `dsp_op`,
`deadPixelsIndices`, `centers`, `bins` and `nPixelsPerBin`. Some app versions
stored upgrade payloads in SharedPreferences as Base64 containing a four-byte
little-endian checksum followed by a body.

`scio.firmware` can scan such XML/backup artifacts, extract bodies, compare
checksums with device headers, detect Blackfin LDR structure, and report
entropy. A high-entropy result is reported as opaque; it is not automatically
called encrypted or Lockbox-protected.

The original APK/ZIP containers in `<SCIO_DECOMPILED_ROOT>` were
also enumerated directly (not just their decompiled trees). Their `assets/`
entries contain fonts/configuration only; the firmware-named entries are code
and UI resources. No bundled `dsp_*` or per-device table body was found, which
is consistent with the apps downloading upgrades from the service and caching
them only in application data.

## Bounded cryptographic hypothesis

Only after evidence supports encryption, `scio.keyrecover` can test:

- AES modes and explicit IV constructions already represented in the code;
- constants close to cipher signatures in a recovered artifact;
- observed device, Aptina/sensor, DSP, BLE and serial identifiers;
- firmware/DSP/hardware/I2S version strings;
- reversible encodings, standard hashes and bounded pairwise combinations.

Candidate names record the exact derivation. Smoothness is only a pre-screen.
A key is not validated until it produces consistent structure across blobs and
passes held-out calibration/spectrum tests.

## USB probe results (device firmware 147, 2026-09-07)

Windows enumerates one standard CDC-ACM serial interface (`VID_0451`,
`PID_16AA`, revision `0009`, bus description `CP SCIO USB CDC`) and no sibling
DFU, mass-storage, HID, or vendor-specific interface.

- `READ_EVENT_LOG (0x06)`, `PARAMETER_GET (0x08)` and `BIST (0x09)` produced no
  response for the tested payloads.
- `READ_FILE_HEADER (0x87)` returned the same 16-byte header when appended
  offset/length fields were tried.
- Reserved `0x88`, `0x89`, `0x93`, `0x95` acknowledged an empty payload with an
  empty body; `0x8A`–`0x8F` timed out.
- No tested read-only command returned a firmware body. Non-empty reserved
  payloads remain deliberately untested because they may mutate device state.
- A direct serial check after `READ_FILE_HEADER` received one 20-byte frame
  (4-byte response framing plus 16-byte header) and no trailing file data.
- Invalid file IDs 80–86, 93–98 and 104–110 repeatably returned the same fixed
  16-byte sentinel `020aa1021013ffffffffff02101bffff`; ID 88 returned the fixed
  value `7409120ad5e0f509a3e0f50ae5093333`. The value does not vary with the
  requested ID, so this is not evidence of an address-based read primitive.

Recorded headers include:

| file | id | size | version | checksum |
|---|---:|---:|---:|---:|
| BLE runtime (enum discrepancy) | 87 | 119233 | 125 | 12925168 |
| dsp_boot | 90 | 7284 | 17 | 688456 |
| dsp_dec | 91 | 14600 | 12 | 1548938 |
| dsp_op | 92 | 32628 | 147 | 4151168 |
| deadPixelsIndices | 100 | 1714 | 3 | 97267 |
| centers | 101 | 96 | 3 | 6080 |
| bins | 102 | 140 | 3 | 13587 |
| nPixelsPerBin | 103 | 1166 | 3 | 36371 |

This is a negative result for the tested interface and firmware version, not a
proof that every possible software-readable interface is impossible.

## Repeated-capture and transform observations

Five stored burst scans have different bodies, no repeated 16-byte blocks, and
no shared first block. That behavior is compatible with randomized encryption,
but also with compressed or otherwise avalanche-like transforms. The evidence
report generated by `analyze_scio.py` preserves the measurements without
promoting the earlier cipher-mode conclusion.

Thirty additional scans of one unchanged target show the same result. Direct
u8/u12/u16 raster projections have no repeatable pixel structure, so a plain
image payload is not supported. Identifier-derived AES/TEA/XTEA searches using
cross-scan plaintext repeatability, and bounded LCG/xorshift/MT/SHA-counter
stream transforms, also produced no hit. See `EVIDENCE.md` and the JSON reports
under `analysis_output/` for exact candidate counts and scores.

## Current software-only route

1. Inventory every local capture and archived spectrum.
2. Collect the controlled replicate matrix in `EVIDENCE.md`.
3. Discriminate packing, compression, obfuscation and encryption statistically.
4. Search local artifacts for tables or executable bodies.
5. Implement only a transform that generalizes across held-out sessions.
6. If cryptographic opacity is established without local key/implementation,
   record the exact blocker instead of generating a plausible-looking curve.
